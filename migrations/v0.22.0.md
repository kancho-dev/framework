# v0.22.0 — Analyzer Report Contract And Optional Multi-Machine Aggregation

This release replaces the Tokens / Cost Analyzer's generated `normalized.json` with a new `report.v1.json` contract, adds optional multi-workspace and multi-machine aggregation, and adds optional immutable old-machine archives to Session Browser. The analyzer artifact change is breaking for anything that read the old file; the Session Browser archive capability and everything else are additive and opt-in.

Existing workspaces keep working untouched. The analyzer regenerates its artifacts from your session data, which this release does not touch, so a workspace that only uses the dashboards needs no data migration and no configuration. Analyzer aggregation and Session Browser archives are both off unless configured.

## Breaking changes

**Two generated artifacts are withdrawn with no compatibility shim.**

- `.tools-config/tokens-cost-analyzer/normalized.json` is replaced by `report.v1.json`. The new artifact is not a rename: it adds a report header and an `origin` block, gives every record `unitId`, `identityClass`, `contentFingerprint`, `workspaceId`, and `derivation`, and redacts absolute paths, because this file is what another machine fetches when you aggregate. Anything that parsed the old shape must be updated, not just repointed.
- `.tools-config/tokens-cost-analyzer/report.md` is no longer written (withdrawn earlier in this release). Nothing consumed it and the same information is in the web UI; CLI runs now emit only their `Wrote N records` line.

A workspace loses nothing it was using through the dashboard, the Cockpit widget, or the `/api/report` endpoint — all three are unchanged or extended. What breaks is any consumer **outside** the framework that read those files directly.

## Required checks

1. Find anything outside the framework that reads `.tools-config/tokens-cost-analyzer/normalized.json` or `report.md` — a personal script, a scheduled export, a spreadsheet feed, another tool — and move it to `report.v1.json` or the analyzer's `/api/report` endpoint. Expect to update field access, not only the filename. If nothing reads them, this release needs no data work from you.
2. Run the analysis once after updating: open the analyzer dashboard, or run `node framework/tools/tokens-cost-analyzer/analyze.mjs --workspace "$PWD"`. This writes `report.v1.json`, `daily.json`, and `scan-scope.json`, and removes the orphaned `normalized.json` for you. Until it runs, the dashboard reports that session deep links are unavailable rather than showing them as broken.

## Optional checks

3. Delete a leftover `report.md` from your analyzer output directory. Nothing writes it, nothing reads it, and nothing removes it for you — it is inert, so this is housekeeping rather than a fix.
4. Delete a leftover `normalized.json` **only in output directories you no longer analyze**. A normal re-run (check 2) deletes it automatically, so this applies to a directory you have stopped using, a second workspace you do not intend to re-analyze, or a custom `TOKENS_COST_ANALYZER_OUT` location you have retired. The file is large and unread, so removing it is worthwhile if you are tidying; leaving it costs only disk.
5. Break one machine's usage down by project by declaring workspace partitions in `.tools-config/tokens-cost-analyzer/sources.json` under `self`. Partitions divide your existing totals rather than narrowing them — the overall number is unchanged and the By Workspace panel gains rows that sum to it.
6. Combine machines by adding `sources[]` entries to the same file. **Read the posture change before you do**: `type: "ssh"` sources make outbound SSH connections to the hosts you name, running one bounded read of a report the remote already generated. Credentials stay in your `ssh_config` and agent, never in the tool's configuration. `type: "file"` sources need no network. Reports are fetched **compressed** (`gzip -c`, ~19× smaller for a 100 MB report) with decompression bounded by `maxReportBytes`; a remote without `gzip`, or a key still restricted to `cat`, falls back automatically, so an existing `authorized_keys` restriction keeps working — update it to `command="gzip -c <path>"` to get the compression. Fetches happen on a bounded cadence in the background rather than on every page load, so once a machine has given you a report, a dashboard request never waits on it again — only the very first fetch of a newly configured source is awaited. See `tools/tokens-cost-analyzer/README.md` for configuration, the optional `authorized_keys` restriction, and the freshness thresholds.
7. Keep a **retired machine's** history in your totals by copying its `report.v1.json` to `.tools-config/tokens-cost-analyzer/archive/<id>.json` and adding `{ "id": "<id>", "type": "archived" }` to `sources[]`. Copy it *before* decommissioning — there is no way to regenerate it afterwards — and back up `archive/`, which is the one directory under `.tools-config/` holding data nothing can rebuild. An archived source needs no network, never goes stale, and renders in a neutral archive tone.
8. If you want session deep links from usage attributed to a catch-all root (for example a scan rooted at your home directory), register a Cockpit workspace at that root with Session Browser enabled, or declare finer `self.workspaces`. A row links only when the session is genuinely reachable from this Cockpit; anything else renders as inert, labelled text on purpose.
9. Before retiring a machine whose coding history matters, build its Session Browser archive with `node tools/session-browser/build-archive.mjs <machine-id>`. Archive files are immutable, non-resumable history and must be backed up: unlike normal `.tools-config/` state, they cannot be regenerated after the old machine is gone. See `tools/session-browser/README.md` for source layout, overwrite safety, OpenCode handling, and the local `machines.json` configuration.
10. For one archive shared by several Cockpit workspaces, declare its roots once with `sessionArchiveManifestPath`, then add explicit `sessionArchiveBindings` per workspace in Tool Orchestrator's `workspaces.json`. Move each old workspace prefix into its own binding; do not infer identity from folder names. A broad Global binding may overlap narrower workspaces intentionally without sharing their writable metadata.
11. To preserve bookmarks, tags, and saved topics from every old workspace, build the archive with `--workspace-config <workspaces.json>`, then bind its generated `metadata/bundle.json` through `metadataBundlePath`. Archived metadata appears automatically as immutable defaults. The first edit creates a complete live override in that current workspace's normal sidecar; **Reset to archived default** removes only that override. There is no metadata-import step in the final workflow.

## Not required

- No conversion, import, or backup of the old artifacts. `report.v1.json` is regenerated from your session data; there is nothing in `normalized.json` worth preserving that the new artifact does not produce.
- No configuration to keep local-only behaviour. Aggregation, the last-known-good `cache/` directory, and all network access appear only if you create `sources.json`.
- No changes to `pricing.json` or `subscriptions.json`. Both are read as before.
- No workspace `AGENTS.md`, task, project, or forced metadata migration. Existing Session Browser metadata stays writable and unchanged unless you opt into an archive and edit an archived session.
- No manual derivation-cache cleanup after the pricing and accounting changes. Versioned semantics invalidate stale shards automatically.
- No archive configuration for current-machine browsing. With no local `machines.json` or shared manifest/bindings, Session Browser behaves as before.
- No explicit archived-metadata import. The final product reads verified archive snapshots as defaults and uses live copy-on-write overrides.
- No need to hand-edit `report.v1.json` or `scan-scope.json`. Both are generated; `scan-scope.json` in particular is local-only and deliberately holds the absolute roots that the shareable report omits, so it should never be copied to another machine or committed.
